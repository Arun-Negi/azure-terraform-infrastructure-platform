# Azure Terraform Infrastructure Platform

Deploy Azure resource groups, optional virtual networks, and subnets by editing **one JSON file**. End users do not need to edit Terraform variables or HCL.

## Configure one JSON file

Copy the example to the automatically loaded Terraform input filename:

```bash
cp terraform.tfvars.json.example terraform.tfvars.json
```

Edit `terraform.tfvars.json`. The shared naming settings are simple top-level fields (`org`, `app`, `env`). Add one object per resource group; networking is optional and only needs to be included where required.

```json
{
  "subscription_id": "00000000-0000-0000-0000-000000000000",
  "org": "acme",
  "app": "platform",
  "env": "dev",
  "resource_groups": [
    {
      "instance": "core",
      "virtual_network": {
        "instance": "main",
        "address_space": ["10.10.0.0/16"],
        "subnets": [
          { "instance": "app", "address_prefixes": ["10.10.1.0/24"] },
          { "instance": "data", "address_prefixes": ["10.10.2.0/24"] }
        ]
      }
    },
    {
      "instance": "monitoring"
    }
  ]
}
```

This example creates two resource groups, one VNet, and two subnets. Tags are optional; add a `tags` object only when needed. Add or remove objects in `resource_groups` to control the number of resource groups.

### Naming convention

All resource names are generated by the shared `modules/naming` module using:

```text
{org}-{app}-{env}-{type}-{instance}
```

The example generates names such as `acme-platform-dev-rg-core`, `acme-platform-dev-vnet-main`, and `acme-platform-dev-snet-app`.

- `org`: 2-12 lowercase letters/digits, optionally separated by single hyphens.
- `app`: 2-16 lowercase letters/digits, optionally separated by single hyphens.
- `env`: one of `dev`, `test`, `qa`, `stage`, `prod`, `shared`, or `sandbox`.
- `instance`: user-controlled identifier for each resource group, VNet, and subnet (for example, `core`, `main`, `app`, or `data`).
- `type` is platform-controlled: `rg`, `vnet`, or `snet`; users cannot override it.
- `virtual_network` is optional. If included, `address_space` is required; `subnets` are optional.
- `address_prefixes` contains subnet CIDR ranges.
- Region is fixed to Central US (`centralus`); users cannot override it in JSON.

The JSON Schema provides editor validation for fields and component lengths. The naming module validates the complete generated name against Azure limits before planning: resource groups 90 characters, VNets 64, and subnets 80. Shorten `org`, `app`, `env`, or the relevant `instance` if the final name is too long.

## VS Code JSON IntelliSense

The repository includes `schemas/terraform-input.schema.json` and `.vscode/settings.json`. Open the repository folder in VS Code and edit `terraform.tfvars.json` for field descriptions and validation hints.

1. Open the repository folder in VS Code.
2. Copy the example: `cp terraform.tfvars.json.example terraform.tfvars.json`.
3. Edit the JSON; use the schema hints and hover descriptions.
4. Run `terraform validate` and `terraform plan` before applying.

The schema catches common input mistakes, but Terraform and Azure remain authoritative for rules such as CIDR overlap, subnet containment, and name conflicts.

## Toolchain versions

- **Terraform CLI:** minimum supported version is `1.16.6`; CI pins `1.16.6`.
- **AzureRM provider:** pinned to `5.9.0` in `versions.tf`. Review the [official AzureRM 5.0 upgrade guide](https://registry.terraform.io/providers/hashicorp/azurerm/5.0.0/docs/guides/5.0-upgrade-guide) before applying to existing state.
- AzureRM 5.x provider registration behavior is configured in `versions.tf`; the deploying identity must have permissions matching that setting.
- Commit `.terraform.lock.hcl` after initializing on supported platforms.

## Deploy

1. Install Terraform 1.16.6 and Azure CLI.
2. Authenticate using your approved Azure identity and confirm the target subscription.
3. Copy and edit the JSON input file.
4. Run:

```bash
terraform init
terraform fmt -check -recursive
terraform validate
terraform plan -out=tfplan
terraform apply tfplan
```

Review the plan before applying. Replace the placeholder subscription ID. Never commit real input files, state, or secrets. Use a secure remote backend and least-privilege identity for team/CI use.

## Delete resources safely

Resources are removed by changing the JSON input so it no longer declares the resource, then reviewing and applying a Terraform plan. **Removing an object from JSON does not delete anything until an apply is performed.**

### Delete a resource group

Remove its object from the `resource_groups` array. For example, to remove the `monitoring` resource group, keep only the `core` object:

```json
"resource_groups": [
  {
    "instance": "core"
  }
]
```

Terraform will propose destroying the resource group and any resources it manages inside it. Azure may also contain resources in that group that are not managed by this configuration, so check the impact carefully.

### Delete a subnet

Remove only that subnet's object from the VNet's `subnets` array. Keep the VNet and resource-group objects if you want them to remain.

### Delete a virtual network

Remove the `virtual_network` object from the relevant resource group. Terraform will propose removing the VNet and its managed subnets. Review the plan for dependent resources before proceeding.

### Review before deletion

Run the plan and inspect every proposed destroy action:

```bash
terraform plan -out=tfplan
terraform show tfplan
```

If the plan contains only the intended changes, apply the reviewed plan:

```bash
terraform apply tfplan
```

Do not apply a plan if it proposes unexpected deletions. Keep Terraform state safe and backed up. This repository's GitHub Actions workflow is a **validation-only** pipeline: even when run manually, it does not deploy or delete Azure resources. A separate authenticated deployment workflow with appropriate approval controls would be required to apply infrastructure changes from GitHub Actions.

## Validation and governance

GitHub Actions checks Terraform formatting, JSON syntax, configuration validation, and offline Terraform tests with a mocked AzureRM provider. These checks do not deploy resources or guarantee Azure will accept a live request.

The `policies/azure-policy/` directory contains custom policy definitions for allowed locations and the `managed_by` tag. They are not assigned automatically; an authorized Azure administrator must review and assign them.

## Production hardening

- Configure an Azure Storage remote backend with restricted access and state locking.
- Use GitHub Actions OIDC and separate least-privilege plan/apply identities.
- Pin GitHub Actions to immutable commit SHAs.
- Test in a non-production subscription and inspect every plan; resource removals may destroy infrastructure.
- Azure resources can incur charges. Confirm the subscription and plan before applying or destroying.
