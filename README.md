# Azure Terraform Infrastructure Platform

Deploy Azure resource groups, optional virtual networks, and subnets by editing **one JSON file**. End users do not need to edit Terraform variables or HCL.

## Configure one JSON file

Copy the example to the automatically loaded Terraform input filename:

```bash
cp terraform.tfvars.json.example terraform.tfvars.json
```

Open `terraform.tfvars.json` and change the subscription ID, resource group names, tags, and optional network details. The example below creates two resource groups, one VNet, and two subnets:

```json
{
  "subscription_id": "00000000-0000-0000-0000-000000000000",
  "naming": {
    "org": "acme",
    "app": "platform",
    "env": "dev"
  },
  "resource_groups": [
    {
      "instance": "core",
      "tags": {
        "environment": "dev",
        "managed_by": "terraform"
      },
      "virtual_network": {
        "instance": "main",
        "address_space": ["10.10.0.0/16"],
        "subnets": [
          { "instance": "app", "address_prefixes": ["10.10.1.0/24"] },
          { "instance": "data", "address_prefixes": ["10.10.2.0/24"] }
        ]
      }
    },
    {
      "instance": "monitoring",
      "tags": {
        "environment": "shared",
        "managed_by": "terraform"
      }
    }
  ]
}
```

### Naming convention

All supported resource names are generated by the shared `modules/naming` module using:

```text
{org}-{app}-{env}-{type}-{instance}
```

For the example above, names include `acme-platform-dev-rg-core`, `acme-platform-dev-vnet-main`, and `acme-platform-dev-snet-app`.

- `naming.org`: 2-12 lowercase letters/digits; keep short because it prefixes every resource.
- `naming.app`: 2-16 lowercase letters/digits.
- `naming.env`: one of `dev`, `test`, `qa`, `stage`, `prod`, `shared`, or `sandbox`.
- `instance`: user-controlled identifier on each resource group, VNet, and subnet. Use a meaningful value such as `core`, `main`, `app`, `data`, or `001`.
- `type` is platform-controlled: `rg`, `vnet`, or `snet`. Users cannot override it.
- `tags` (optional): key/value tags.
- `virtual_network` (optional): add this object only when the resource group needs a VNet.
- `address_space` and `address_prefixes`: VNet and subnet CIDR ranges.
- **Location is fixed to Central US** (`centralus`); users do not supply it.

The JSON Schema validates component types, patterns, and component lengths in VS Code. The naming module validates the *complete generated name* against each Azure resource's limit before planning: resource groups 90 characters, VNets 64, and subnets 80. Since standard JSON Schema cannot calculate the final length from multiple sibling fields, Terraform performs that cross-field length check. Shorten the org/app/env prefix or that resource's instance if the complete name exceeds its limit.

To add resources, add objects to the appropriate JSON array. To omit networking for a resource group, omit its `virtual_network` property. Keep resource names stable between applies; renaming or removing resources can cause Terraform to replace or destroy infrastructure.

### VS Code JSON IntelliSense

The repository includes a JSON Schema at `schemas/terraform-input.schema.json` and a workspace setting at `.vscode/settings.json`. When you open this repository in VS Code and edit `terraform.tfvars.json`, IntelliSense provides suggestions and validation for naming components, resource instance fields, required fields, and CIDR formatting.

1. Open the repository folder in VS Code (not just the JSON file by itself).
2. Copy the example: `cp terraform.tfvars.json.example terraform.tfvars.json`.
3. Open `terraform.tfvars.json` and place the cursor inside an object to see suggestions; hover over a property to read its description.
4. Follow the schema hints, then run `terraform validate` and `terraform plan` before applying.

The schema catches common input mistakes in the editor, but it cannot validate every Azure rule (such as CIDR overlap, whether a subnet fits inside its VNet, or whether a name already exists in Azure). Terraform validation and the Azure provider remain authoritative.

## Toolchain versions

- **Terraform CLI:** minimum supported version is `1.16.6`; the validation workflow pins `1.16.6` for reproducible CI runs. Use a compatible stable Terraform 1.x release locally.
- **AzureRM provider:** pinned to `5.9.0` in `versions.tf` so CI and local runs use the same provider release. This is a major upgrade from 4.x; review the [official AzureRM 5.0 upgrade guide](https://registry.terraform.io/providers/hashicorp/azurerm/5.0.0/docs/guides/5.0-upgrade-guide) before applying this version to an existing state.
- AzureRM 5.x no longer registers Azure resource providers by default. This configuration requests registration of `Microsoft.Resources` and `Microsoft.Network`; the deploying identity must have permission to register them. If your organization centrally manages provider registration, pre-register them and adjust this setting to match that governance model.
- Commit `.terraform.lock.hcl` after running `terraform init` on the supported platforms to record provider checksums and selections.

## Deploy

1. Install Terraform 1.16.6 or a newer compatible stable 1.x release, and Azure CLI.
2. Authenticate using your approved Azure identity and confirm the target subscription.
3. Copy and edit the JSON input file as described above.
4. Run:

```bash
terraform init
terraform fmt -check -recursive
terraform validate
terraform plan -out=tfplan
terraform apply tfplan
```

Review the plan before applying. The sample subscription ID is a placeholder and must be replaced. Never commit real input files, Terraform state, or secrets. Use a secure remote backend and least-privilege identity for team/CI use.

## Validation and governance

Terraform validates resource group names, duplicate names, VNet/subnet names, and CIDR syntax before deployment. GitHub Actions checks Terraform formatting, JSON syntax, configuration validation, and offline Terraform tests with a mocked AzureRM provider. These checks do not deploy resources or guarantee Azure will accept a live request.

The `policies/azure-policy/` directory contains custom policy definitions for allowed locations and the `managed_by` tag. They are not assigned automatically; an authorized Azure administrator must review and assign them at the appropriate scope.

## Production hardening

- Configure an Azure Storage remote backend with restricted access and state locking.
- Use GitHub Actions OIDC and separate least-privilege plan/apply identities.
- Pin GitHub Actions to immutable commit SHAs.
- Test in a non-production subscription and inspect every plan; resource removals may destroy infrastructure.
- Azure resources can incur charges. Confirm the subscription and plan before applying or destroying.
